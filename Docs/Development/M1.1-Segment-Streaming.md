# M1.1 Movement Correction and Segment Streaming

## Why the grounded sphere did not move

The motor deliberately freezes Rigidbody rotation because the physical root
must not roll. The collider still used Unity's ordinary friction, so the floor
contact solver cancelled horizontal sliding. The motor kept requesting 7 m/s,
but measured speed returned to zero after every physics step. Jumping removed
floor contact, which is why horizontal movement became visible in the air.

M1.1 assigns a zero-friction `PhysicsMaterial` to the SphereCollider. The
Rigidbody can now translate while the collider-free child shell supplies visual
rotation. Minimum friction combination ensures the player's zero value wins
when touching ordinary corridor surfaces.

## Static world, moving player

Only the player and camera move continuously. Floors, walls, barriers, enemies,
projectiles, and effects can therefore use normal world coordinates and stable
physics. The camera keeps the sphere in a consistent screen region, creating
the same visual impression as a corridor moving right-to-left.

The camera's focus position advances but never retreats. The player can reverse
inside the visible encounter space until reaching a rear boundary projected
from the actual camera viewport. This calculation adapts to aspect-ratio changes
instead of relying on a guessed world distance.

## Definition versus instance

A segment type and a segment occurrence are deliberately different concepts:

| Concept | Responsibility |
|---|---|
| `CorridorSegmentDefinition` | Stable ID, length, and prefab for one type |
| `CorridorSegmentInstance` | One live occurrence with sequence and world boundaries |
| `CorridorSegmentStreamer` | Keeps three instances, retires the rear one, creates the next |
| Future seeded planner | Chooses which definition should appear next |

Three live instances cover the current view and look-ahead. A segment is
retired only when its far edge and a safety margin are behind the measured rear
camera boundary. The next definition is then instantiated directly after the
farthest live edge. Because placement uses each definition's own length, future
types can be shorter or longer without gaps or overlap.

M1.1 has only the `movement_training` definition, so selection repeats that
prefab. The round-robin selection method is intentionally isolated. M4 will
replace that policy with the deterministic seeded planner while retaining the
same creation and retirement lifecycle.

We currently use `Instantiate` and `Destroy` because segment transitions are
infrequent and this is the clearest correct implementation for one developer.
If player-build profiling later reveals a transition hitch, the two lifecycle
methods can acquire and release instances from per-prefab pools without changing
segment definitions or the planner.

## Revised proportions

- Sphere radius: 0.6 m when the old 0.75 m default was untouched.
- Corridor internal width: 12 m.
- Wall height: 0.9 m.
- Segment length: 40 m, longer than the intended viewport.
- Camera: higher, more overhead, stable vertical focus, forward-only progress.

The migration changes legacy tuning only when it still exactly matches M1
defaults. Existing deliberate Inspector changes are preserved.

## Adding another segment type later

1. Create a prefab whose pivot is at its horizontal center and floor height.
2. Add `CorridorSegmentInstance` to the prefab root.
3. Create a `CorridorSegmentDefinition` asset.
4. Give it a unique stable ID, exact length, and prefab reference.
5. Add the definition to the streamer's available definitions.

This manual round-robin list is suitable for labs. Production generation will
choose definitions through seed, difficulty, connector, and fairness rules.
